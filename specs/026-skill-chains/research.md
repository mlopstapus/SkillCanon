# Research: Skill Chains

No `[NEEDS CLARIFICATION]` markers remained in spec.md (the `/speckit-clarify` session resolved the 4 real ambiguities: start/advance authorization scope, and race/terminal-state handling for `advanceSkillChainRun`). This document instead captures the concrete engineering decisions needed to turn the already-detailed spec/backlog/CONTRACT.md into a buildable design — each one either fills a gap those documents left open, or confirms an existing codebase pattern this feature reuses rather than reinvents.

## Decision: how a chain version is discriminated from a template version

**Decision**: Add two columns to `prompt_registry.prompt_versions`: `kind` (`text`, enum `["template", "chain"]`, `NOT NULL`, `DEFAULT 'template'`) and `steps` (`jsonb`, nullable). `publishVersion` computes `kind` from which shape the caller provided — never accepted as a caller-supplied field — and rejects a call providing both `steps` and template content, or neither.

**Rationale**: Backlog line 19 is explicit: "a `PromptVersionSummary`'s kind... is an explicit discriminant, not inferred from which fields happen to be null." A `DEFAULT 'template'` on the new `NOT NULL` column means the migration backfills every existing row without a data-migration script — every row published before this feature is unambiguously a template, which is simply true.

**Alternatives considered**:
- *Infer kind from `steps IS NOT NULL`* — rejected outright by the backlog's own wording (explicit discriminant required), and it would make a future "chain version with metadata but zero steps" (spec FR-010 — a valid, real case) ambiguous with "not a chain."
- *Separate `chain_versions` table, FK to `prompt_versions`* — rejected: doubles the query surface for every version-reading caller (`expand()`, `listVersions`, project assignment, etc.) for no benefit; the "exactly one of two shapes" spec requirement is naturally a same-row constraint, not a cross-table one.

## Decision: `publishVersion` shape validation

**Decision**: A new pure domain function, `determinePromptVersionKind(params: PublishVersionParams): "template" | "chain"`, throws a new `InvalidVersionShapeError` if `params.steps` is given alongside a non-null `systemTemplate`/`userTemplate`, or if none of `steps`/`systemTemplate`/`userTemplate` is given at all. `publishVersion` calls this before any DB write and stores the returned `kind` alongside `steps` (null for a template version).

**Rationale**: Matches FR-001 exactly ("exactly one of the two, mixing both or specifying neither is rejected"). This is a **behavior tightening** versus today's shipped `publishVersion`, which currently accepts a version with both `systemTemplate`/`userTemplate` omitted with no rejection at all — flagged here, not silently changed, since it's a real (if narrow) behavior change for template versions too, not just new chain-version validation.

## Decision: chain-step dependency validation (run-time, not publish-time)

**Decision**: A new pure domain function, `validateChainSteps(steps: ChainStep[]): void`, throws `InvalidChainDependencyError` if any step's `dependsOn` references a step id that doesn't exist in the chain, references the step's own id, or references a step at the same or a later array position — and also if two steps share the same `id` (an edge case spec.md calls out explicitly, folded into the same check since it's the same "structurally invalid chain" class of error). Called once, by `startSkillChainRun`, before any run row is created (FR-006) — never at `publishVersion` time (backlog line 20: "never validated for cycles or that referenced ids exist at publish time").

**Rationale**: Backlog explicitly assigns this validation to run-start time, not publish time, since "chain resolution order is strictly sequential by step position — never dependency-graph order" (CONTRACT.md Stability Guarantees) makes "later position" a well-defined, cheap check without needing real cycle detection (a step can never depend on anything at or after its own position, so no cycle can ever exist in a chain that passes this check — the position-ordering rule *is* the cycle-prevention rule).

## Decision: per-step input mapping for `dependsOn`

**Decision**: When resolving step *N* via `expand()`, the `input` passed is built from *only* that step's `dependsOn` list: for each `depId` in `step.dependsOn`, look up the already-resolved run-step whose chain-step id is `depId` and set `input[depId] = { status: "success" | "error", output: <string | null> }`. A step with an empty `dependsOn` (always true for step 0, since nothing can precede it) gets `input: {}`. There is no separate, caller-supplied "run input" parameter anywhere in the chain-run API surface — `startSkillChainRun` takes no `input` argument (per its already-fixed CONTRACT.md signature), so inter-step data flow is the *only* input source for any step after the first.

**Rationale**: Directly implements spec FR-008 ("a later step... receives an explicit result-unavailable indicator... wherever that dependency would otherwise have been filled in") and User Story 2's acceptance scenarios. Wrapping every dependency in a uniform `{ status, output }` envelope (rather than putting `null` directly at the key) means a template author can write `{% if step1.status == "success" %}...{% endif %}` — a real, unambiguous way to branch on failure, which a bare `null` value could not distinguish from "the step succeeded but reported no output" (a separate, legitimate state per FR-007, where `output` is optional).

**Alternatives considered**: A single sentinel string (e.g. `"__UNAVAILABLE__"`) in place of the whole envelope — rejected as strictly worse for template authors (string-comparison-based branching instead of a real boolean-ish field) with no compensating simplicity gain, since the envelope is exactly as easy to construct.

## Decision: run state machine and step resolution loop

**Decision**: `skill_chain_runs.status` is one of `"in_progress" | "completed" | "failed" | "abandoned"`. `current_step_index` names the step the caller must report on next (the last step returned to a caller and not yet reported). The loop:

- **`startSkillChainRun`**: resolve the chain version (must be `kind: "chain"`, else `NotAChainVersionError`), authorize (see below), validate steps, then:
  - Zero steps: insert the run row already `status: "completed"`, `currentStepIndex: 0`, `startedAt = completedAt = now()`, write the `skill_chain_run.completed` audit event, return `{ runId, done: true }`.
  - Otherwise: insert the run row (`status: "in_progress"`, `currentStepIndex: 0`), resolve step 0 via `expand()` (its `input` is always `{}` since nothing can precede it), insert its `skill_chain_run_steps` row (`reportedStatus: null`), return `{ runId, step: resolution }`.
- **`advanceSkillChainRun(db, actor, runId, report)`**: inside one transaction, `SELECT ... FOR UPDATE` the run row (locks it against concurrent advance calls on the same run — see Concurrency below). If not found (or not accessible — same "looks like not-found" rule as authorization below): `RunNotFoundError`. If `status !== "in_progress"`: `RunAlreadyFinishedError` (FR-007b). Otherwise, record `report` (`status`, `output?`, `error?`) onto the pending `skill_chain_run_steps` row at `currentStepIndex`. If that was the last step: mark the run `completed` (every step succeeded) or `failed` (any step, including this one, was reported `"error"`) with `completedAt = now()`, write the matching audit event, return `{ done: true }`. Otherwise: resolve the next step via `expand()` (its `input` built per the mapping above, from every run step resolved so far — not just the one just reported, since `dependsOn` can reference any earlier step, not only the immediately preceding one), insert its row, bump `currentStepIndex`, return `{ step: resolution }`.
- **`abandonSkillChainRun(db, actor, runId, auditContext?)`**: same row-lock/terminal-state check as `advanceSkillChainRun`, then sets `status: "abandoned"`, `completedAt = now()`, writes `skill_chain_run.abandoned`. No step report involved — the pending step, if any, is simply left with `reportedStatus: null` forever (a real, meaningful "never got a chance to run" state for history review, distinct from a reported failure).

**Rationale**: A run's failure/success determination requires seeing *every* step's outcome, not just the last one (spec Acceptance Scenario "every step through the second-to-last succeeded and the final step failed → run status reflects failure") — so the loop always walks every step regardless of intermediate failures, only the *overall* status reflects whether any step failed. This matches CONTRACT.md's "Prompt Registry does not decide success/failure itself; it only propagates what the caller reported" framing exactly.

## Decision: `ChainStepReport` must name its own step index (correction found while writing the concurrency test)

**Decision**: `ChainStepReport` gains a required `stepIndex: number` field (beyond CONTRACT.md's originally documented `{ status, output?, error? }`). `advanceSkillChainRun` rejects with `RunStepConflictError` whenever `report.stepIndex !== run.currentStepIndex`, checked immediately after acquiring the row lock and confirming the run is `in_progress`.

**Rationale**: While writing the FR-007a concurrency test, it became clear the original design (no step reference on the report at all) cannot actually distinguish "a stale network-retry duplicate of an already-processed report" from "a legitimate new report for whatever step is now current" — both look identical to the function (an opaque `{status, output?, error?}` blob), regardless of row locking. Row locking alone only serializes *access*, it doesn't carry *intent*: a losing call, once unblocked, would previously have gone on to process its report against the *new* current step — silently misattributing a stale report rather than rejecting it, exactly the failure mode FR-007a exists to prevent. Every `ChainStepResolution`/`StartRunResult`'s `step` already carries `stepIndex` back to the caller, so a well-behaved caller always has it on hand to echo back — this closes a real gap rather than asking callers for something they don't already have.

**Alternatives considered**: Detecting "was this call blocked by lock contention" some other way (e.g. a `pg_advisory_lock` wait-time check) — rejected as fragile and indirect compared to just asking the caller which step it means, which also has the advantage of catching a *non-concurrent* stale/duplicate call (e.g. a caller that simply calls twice in sequence by mistake, no race involved at all) that pure lock-contention detection would never catch.

## Decision: concurrency and terminal-state rejection (clarify-session answers)

**Decision**: `SELECT ... FROM skill_chain_runs WHERE id = $1 FOR UPDATE` inside `advanceSkillChainRun`'s (and `abandonSkillChainRun`'s) own transaction is the entire mechanism. A second, racing call for the same run blocks on the row lock until the first commits, then re-reads the now-updated row and finds `currentStepIndex` has moved past what it expected (or `status` is no longer `"in_progress"`) — both already-planned checks (`RunAlreadyFinishedError`, and a new `RunStepConflictError` when the pending step it expected to report against no longer matches) naturally catch this, no extra bookkeeping column needed.

**Rationale**: The shared `timestamps()` column helper's own doc comment states "the kernel does not provide optimistic-concurrency conflict detection" — this repo deliberately does not have an `updated_at`-based compare-and-swap convention to reuse. Postgres row-level locking is the correct native tool for "at most one accepted report per pending step" (FR-007a) and requires no new column or library. This is function-local to the chain-run flow, not a change to the shared kernel.

**Alternatives considered**: An optimistic `WHERE current_step_index = $expected AND status = 'in_progress'` conditional `UPDATE ... RETURNING` (no explicit lock) — functionally equivalent and slightly less code, but rejected because it can't distinguish "this run doesn't exist" from "this run moved on" from one `UPDATE` alone without a follow-up `SELECT` anyway (needed either way to produce the right error type for the caller), so it doesn't actually save a round trip once real error-type fidelity is required.

## Decision: system-side step-resolution failure (FR-011), distinct from a caller-reported failure

**Decision**: When `expand()` throws while resolving a step (`startSkillChainRun` resolving step 0, or `advanceSkillChainRun` resolving the next step) — most concretely `ExpansionSourceNotFoundError` because the step's target skill was deprecated or deleted after the chain was published — the surrounding chain-run function lets a dedicated `ChainStepResolutionFailedError(stepId, promptName, cause)` propagate and roll back the entire call, exactly like any other validation failure in this function (e.g. `InvalidChainDependencyError`). Concretely: `startSkillChainRun` leaves **no run row at all** when step 0 fails to resolve; `advanceSkillChainRun` leaves the run in exactly the state it was in before the call — still `in_progress`, at the same pending step, with the report the caller just supplied for the *previous* step rolled back too, since it was never durably accepted by a call that ultimately failed.

**Rationale (revised during implementation)**: The original design (this section's first draft) tried to persist `status: "failed"` and an audit event *in the same call* that also throws — this cannot work in this codebase's transaction model and was caught by a failing test, not by review. Every caller of a Prompt Registry application function wraps the call in `withTenantContext`, which opens **one** outer transaction and hands it down as the `db`/`tx` parameter every application function receives — there is no way for code running through that handle to commit a "consolation" write independently of whatever the surrounding call ultimately does. A `db.transaction()` call made *inside* an already-open transaction is a nested savepoint, not an independent commit: if the outer scope subsequently throws (as this function must, to satisfy "distinguishable from a caller-reported failure"), the outer rollback undoes every nested savepoint too, savepoint-release notwithstanding. The only way to genuinely persist state independently of the throw would be a second, separate DB connection bypassing the caller-supplied `db` parameter — which would violate this codebase's universal convention that every application/repo function operates only through the `db`/`tx` handle it's given, never a directly-imported client singleton.

Once that constraint is accepted, "throw and roll back entirely" turns out to be the *more* correct semantic anyway, not just the only implementable one: (1) the caller still gets a **thrown error**, structurally distinct from any normal `{ step }`/`{ done: true }` return value — satisfying "immediate and distinguishable" without needing a persisted marker at all; (2) for `advanceSkillChainRun`, leaving the run retryable in `in_progress` at its current step (rather than permanently `failed`) is a better fit for what's often a transient condition (the target skill could be republished, or the underlying cause could simply be a blip) — the caller can retry the same `advanceSkillChainRun` call once the underlying issue clears, or call `abandonSkillChainRun` to give up outright, the same two options already available for any run a caller stops advancing for any other reason (spec Assumptions — no auto-expiry).

**Alternatives considered**: Silently treating a resolution failure the same as a caller-reported `"error"` (insert a run-step row with a synthetic `reportedStatus: "error"`) — rejected outright, since it's exactly the conflation FR-011 says must not happen. Persisting a "failed" marker via a second, independent DB connection — rejected as an architectural violation (see above); no other function in this codebase reaches for a connection outside the one it's given, and this feature shouldn't be the first.

## Decision: enforcing the 64 KB opaque-output cap (FR-014)

**Decision**: `advanceSkillChainRun` validates `report.output`'s length **before** opening its transaction (a cheap, pure check — no DB round trip needed to reject). A value exceeding 64 KB (measured in UTF-8 bytes, matching how Postgres itself measures `text` size) throws a new `ReportOutputTooLargeError` immediately — the run's state is left completely untouched (still `in_progress`, same pending step, same `currentStepIndex`), so a caller that hit the cap can simply retry with a smaller value without having lost its place in the run.

**Rationale**: FR-014 (tightened by `/speckit-analyze` finding C2) requires the caller to "always know definitively whether its full result was recorded" — silent truncation would violate that outright (the caller would believe its full value was stored when it wasn't), and truncating whatever arbitrary opaque byte string the caller sent is also more "interpreting" the content than this system does anywhere else (FR-014's own opaque-data guarantee). Rejecting outright, with no state change, is both the simplest implementation and the only option consistent with both halves of FR-014 at once.

**Alternatives considered**: Truncate to 64 KB and proceed — rejected per above. Cap enforcement inside the transaction (after the row lock) — rejected as unnecessary; nothing about the cap check depends on any data only visible after locking the run row, so doing it first avoids taking a lock for a request that's going to be rejected anyway.

## Decision: authorization for start/advance/abandon (clarify-session answer applied)

**Decision**: A new small helper, `assertSkillAccessible(db, actor, prompt)` in `application/authorize-chain-run-action.ts`, calls the same `listAccessibleByOwnerAndSubscriptions` repo query `listPrompts` already uses and checks the target prompt id is present in the result. On failure, throws the existing `PromptNotFoundError` — the *same* error a genuinely nonexistent skill name would produce, never a distinguishing "found but not authorized" error.

**Rationale**: Directly implements the clarify session's accepted answer ("anyone who can already access the skill... the same accessible-skill set used everywhere else"). Reusing the exact same error class as not-found matches this codebase's established convention (documented repeatedly elsewhere in this repo, e.g. RLS cross-org denial) that access denial must never be distinguishable from nonexistence, to avoid confirming a private skill's existence to a user without access to it.

**Scope note**: This checks the *default* accessible set only (owner/own-team/direct-subscription/project-member-of-a-project-that-subscribes) — it does **not** additionally widen access via project-*assignment* the way `listPrompts(db, actor, { projectId })`'s optional parameter does, because `startSkillChainRun`'s already-fixed CONTRACT.md signature takes no `projectId` argument (chain runs, like `expand()` calls without a project context, aren't project-scoped operations). This mirrors `expand()`'s own existing behavior exactly (`projectId` is accepted by `expand()` only to forward into objective resolution, never into access control).

## Decision: RLS for the two new tables

**Decision**: `skill_chain_runs` carries its own `organization_id` column with a direct-equality policy (matching `subscriptions`/`projects`). `skill_chain_run_steps` has no `organization_id` of its own — tenancy resolves via an `EXISTS` join through `skill_chain_runs`, exactly matching the already-shipped `prompt_versions`-through-`prompts` pattern in `0019_prompt_registry_rls.sql`. Both tables get RLS enabled from their very first migration (`ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` + `CREATE POLICY ... TO skillcanon_app`) — no follow-up tenant-isolation feature needed, since these are brand-new tables, not a retrofit (matching backlog line 34's explicit instruction and this repo's established precedent for new `prompt_registry.*` tables since `022-prompt-registry-tenant-isolation`).

**Rationale**: Confirmed via research that this exact two-shape RLS pattern (direct column vs. join-through-parent) is already live in this schema for two analogous relationships — no new pattern invented, straight reuse.

## Decision: "events" are audit-log actions, not a pub/sub mechanism

**Decision**: `SkillChainRunCompleted`/`SkillChainRunFailed`/`SkillChainRunAbandoned` (CONTRACT.md's naming) are implemented as three `record()` calls with actions `skill_chain_run.completed` / `.failed` / `.abandoned`, each wrapped in `withAudit` alongside the run-status-updating mutation, exactly the pattern `create-workflow.ts` and `publish-version.ts` already use. Run *creation* and each intermediate step's resolution are not separately audited (only the three terminal transitions are) — matching CONTRACT.md's Events Published table, which lists only Completed/Failed (this feature adds Abandoned as a third, more precise action — see plan.md Complexity Tracking item 3).

**Rationale**: Research confirmed zero event-bus infrastructure exists anywhere in this codebase — every `CONTRACT.md` "Events Published" table in this repo is, in every existing case, documentation shorthand for "a `record()` call with this action string," not a runtime pub/sub contract. No new infrastructure is introduced by this feature; it follows the same shorthand.

**Consequence flagged, not solved here**: CONTRACT.md's Events Published row also names "Distribution (usage telemetry)" as a consumer. Research confirmed `distribution.recordPromptUsage` has no live caller anywhere yet (not even `expand()`'s own ordinary single-skill invocations) — wiring chain-run completion into it here would be scope creep ahead of where the rest of the codebase already is. See plan.md Complexity Tracking item 4 and the corresponding note added to `backlog/008-distribution/004-usage-telemetry.md`.

## Decision: `abandonSkillChainRun` as a dedicated 5th function

**Decision**: Ending a run early (FR-009) is its own exposed function, not a third pseudo-status on `advanceSkillChainRun`'s `report` parameter.

**Rationale**: `SkillChainStepReport`'s `{ status: "success" | "error" }` (CONTRACT.md's already-fixed data contract) describes an outcome *for the pending step* — abandoning a run isn't a step outcome at all, it's the caller declining to continue. Overloading `report.status` with a third value not covered by that type would either widen a stability-guaranteed public type (a breaking-change-policy concern per CONTRACT.md) or require a parallel `abandon: true` flag that's semantically a completely different operation wearing the same function name. A separate function is the more honest shape and costs nothing extra to implement, test, or call.

## Decision: workflow-orchestration deletion is safe

**Decision**: Delete `src/bcs/workflow-orchestration/` (all of `domain/`, `application/`, `infrastructure/`, `index.ts`, `CONTRACT.md`, `OWNERSHIP.md`) and remove the `workflow`/`workflowSchema` export from `src/shared/db/schemas.ts`, in this feature's own PR — not left running alongside the new chain-version capability.

**Rationale**: Repo-wide grep found zero references to `@/bcs/workflow-orchestration` (or the bare string `workflow-orchestration`) anywhere in `src/` outside that folder itself — no route, no other BC, no test imports it. Both its `CONTRACT.md` and `OWNERSHIP.md` are already marked `Status: Superseded`, pointing at PDR-017. The one live database object it owns, `workflow.workflows`, has **no RLS at all** today (confirmed: no `ENABLE ROW LEVEL SECURITY` for it anywhere in `drizzle/migrations/`) — deleting it removes a pre-existing tenant-isolation gap rather than needing to fix one in place.

## Decision: migration sequencing

**Decision**: Two migrations, generated via `pnpm db:generate` (with `MIGRATION_DATABASE_URL` set per the CLAUDE.md gotcha) after the corresponding `schema.ts`/deletion changes land: `0023_prompt_registry_skill_chains.sql` (the `prompt_versions` column additions, both new tables, and their RLS) and `0024_drop_workflow_schema.sql` (drops `workflow.workflows` and the `workflow` schema itself — generated automatically once `workflowSchema`'s export is removed from `schemas.ts`). Both hand-checked against the known missing-snapshot-files bug (`drizzle/migrations/meta/0007,0008,0010,0011,0013_snapshot.json` absent — CLAUDE.md) before committing, trimming any bogus re-`CREATE TABLE` statements for already-applied tables the way `024-project-usage-metrics-dashboard` had to.

**Rationale**: Two single-purpose migrations (add capability, then remove the superseded one) are easier to review and roll back independently than one combined file, matching this repo's general one-concern-per-migration convention (e.g. `0018`/`0019` were separate despite touching the same BC in the same feature).
