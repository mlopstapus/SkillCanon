# Research: Local Folder Skill Upload

## Context already established by the sibling feature (013-skill-import-and-external-registries/001, spec 036-external-skill-import)

This feature is the second, deliberately-separate half of epic `013-skill-import-and-external-registries`. The first half already shipped a "New Skill" drawer with a "Blank skill" / "Import from link" mode toggle (`src/app/(app)/prompts/new-prompt-drawer.tsx`), backed by a detect → preview/select → confirm-and-create flow:

- `src/bcs/prompt-registry/domain/external-skill-source.ts` — types (`ExternalSkillCandidate`, `ExternalSkillFile`), `parseSkillFrontmatter()` (regex-based `SKILL.md` frontmatter parsing, never throws), error classes.
- `src/bcs/prompt-registry/infrastructure/github-skill-source.ts` — GitHub Contents API calls.
- `src/bcs/prompt-registry/application/fetch-external-skill-source.ts` — orchestrates the fetch, builds candidates, enforces `MAX_FILE_SIZE_BYTES`/`MAX_SUPPORTING_FILES` (from `domain/prompt.ts`) and `MAX_EXTERNAL_SKILLS_PER_SOURCE = 25`.
- `src/app/(app)/prompts/actions.ts` — two Server Actions (`fetchExternalSkillSourceAction`, `importExternalSkillsAction`) wrap the BC calls with a `requireActingUser()` auth check.
- Registration always goes through the existing `createPrompt`/`publishVersion` pair, one independent `withTenantContext` transaction per skill (so one failure/collision doesn't poison the whole batch) — matches `domain/prompt.ts`'s existing `DuplicatePromptNameError`.

This feature reuses that shape (detect → preview/select → confirm) and its underlying creation path, but is a genuinely separate source and code path per the backlog item's own instruction ("keep this genuinely separate... different auth/ownership assumptions... would make the ownership/authorization story harder to reason about").

## Decision: folder selection mechanism

**Decision**: `<input type="file" webkitdirectory multiple>` for the folder picker, plus drag-and-drop of a folder via `DataTransferItem.webkitGetAsEntry()`. Both funnel into the same intermediate shape before anything is read: a list of `{ relativePath, file }` pairs, where `relativePath` is the path relative to the selected root folder (`File.webkitRelativePath` for the input case; reconstructed via recursive `FileSystemDirectoryEntry` traversal for the drag-and-drop case).

**Rationale**: `webkitRelativePath` (despite the vendor-prefixed name, supported in all evergreen browsers including Firefox and Safari today) is the only way to get a whole folder's structure from a single file-picker interaction without a native filesystem API. No new dependency needed.

**Alternatives considered**: The (newer, Chromium-only) File System Access API (`showDirectoryPicker()`) was considered and rejected as the *only* mechanism — it has no Firefox/Safari support, which would silently break the feature for a large share of users. `webkitdirectory` input + drag-and-drop covers both flows named in the spec's Requirements without a browser-support gap; the spec's own edge case ("browser/device does not support selecting a whole folder") already anticipates a graceful degradation path in case both are unavailable (e.g. an older mobile browser).

## Decision: candidate detection rule

**Decision**: any file whose `relativePath` basename is exactly `SKILL.md` marks its **parent directory** as a candidate skill folder. That directory's other direct siblings (non-recursive — files only, not subdirectories) become the candidate's supporting files. This single rule is applied uniformly regardless of nesting depth.

**Rationale**: this generalizes past `001`'s three-fixed-layout detection (root `SKILL.md` / a `skills/` directory / top-level subdirectories) into one rule, because a locally-uploaded folder's structure is more open-ended than a GitHub source — the backlog explicitly names both `.claude/skills/*/` and `.agents/skills/*/` as container conventions, and a single "any `SKILL.md`, wherever it is" rule handles both (and a bare single-skill folder, and any other future container convention) without hardcoding path segments.

**Alternatives considered**: Hardcoding `.claude/skills/*/` and `.agents/skills/*/` as the only recognized container paths (mirroring the backlog's literal wording) was considered and rejected — it would silently fail to detect a skill sitting in some other conventionally-named folder (e.g. a bare `skills/` directory, matching `001`'s own second layout), which the spec's edge cases don't want ("only real skill folders are detected... unrelated content is ignored").

## Decision: what gets read and transmitted (FR-012)

**Decision**: the client only calls `.text()` on files whose `relativePath` falls inside an already-identified candidate directory (i.e., filenames are inspected first via a cheap string check across the full `FileList`/entry tree — no content reads — before any file content is read). Only those candidate-scoped file contents are ever sent to the server, and only when the user confirms the batch (registration time) — nothing is uploaded merely for preview, because detection/parsing (frontmatter, size limits, duplicate names) all happens after that same read, in one pass, via a Server Action.

**Rationale**: satisfies FR-012/SC-005 (no unrelated content ever leaves the device) by construction — there is no separate "upload for scanning, then upload again for creation" round trip that could accidentally transmit more than intended. It also means unlike `001` (which makes one GitHub API network call per directory it walks, hence its `MAX_DIRECTORIES_SCANNED = 50` bound), enumerating a local folder's full structure is a single free, already-in-memory `FileList`/`webkitGetAsEntry()` walk with no network cost — there is no equivalent "calls made while scanning" cost to bound here, which is *why* FR-014's "no fixed batch cap" clarification is a real, defensible product decision rather than an oversight: the practical reason `001` caps at 25 (bounding GitHub API calls during detection) does not apply to a feature that never makes a network call to detect candidates.

**Alternatives considered**: zipping the whole selected folder client-side and uploading the archive was considered and rejected — it would add a new dependency, uploads unrelated content by default (violating FR-012) unless the client also pre-filters files going into the zip (at which point the zip step adds nothing), and every skill file is already small text content bound by the existing 64KB/20-file limits, so there is no real payload-size problem a zip would solve.

## Decision: noise-directory skip-list + File System Access API fast path (2026-08-13 amendment)

**Problem observed**: pointing the folder picker at a large local root (e.g. a whole repo checkout) was very slow in practice, even though FR-012's transfer-layer guarantee above already holds (only candidate-directory *content* is ever read/sent). The actual cost is the **enumeration/walk itself**, which happens before any candidate filtering runs — this repo's own `node_modules` + `.next` + `.git` alone total ~56,000 files. Root motivating scenario (confirmed with the user): skill folders conventionally live under a dotfolder (`.claude/skills/`, `.agents/skills/`), and native OS folder-picker dialogs hide dotfolders from their *browsing* UI by default, so users are effectively forced to select a large visible ancestor just to sweep the hidden skills folder in.

**Decision**: two additive changes, neither altering the `candidateDirectoriesForPaths` rule above (still "any `SKILL.md` path, no exclusions" — pure and unchanged):

1. A fixed skip-list of directory names (`node_modules`, `.git`, `.next`, `dist`, `build`, `out`, `coverage`, `.turbo`, `.cache`, `.venv`, `venv`, `__pycache__`, `target`, `vendor`, `.pnpm-store`, `.nuxt`, `.svelte-kit`, `.output`) is applied as a pre-filter *before* paths ever reach candidate detection (`hasSkippedSegment()` in `local-folder-reader.ts`). For the drag-and-drop walk (`walkEntry()`), this is checked before recursing, so a skip-listed directory's contents are never even listed. For `<input webkitdirectory>`, it's applied to the already-enumerated `FileList` result (can't avoid the native enumeration cost itself, but reduces downstream JS work and keeps behavior consistent across entry mechanisms).
2. A File System Access API (`showDirectoryPicker()`) fast path is added as the primary "Choose folder" mechanism on browsers that support it (Chromium-family), doing the same lazy, skip-list-aware top-down walk as drag-and-drop — this is the only mechanism that avoids the native forced-full-recursive-enumeration cost `<input webkitdirectory>` has, since it lists one directory level at a time and can decide not to descend. `<input webkitdirectory>` remains the fallback for Firefox/Safari.

**Rationale**: this reverses the "reject FSA as the sole mechanism" alternative above only for the *primary* path, not as a replacement — `<input webkitdirectory>` stays as the cross-browser fallback exactly as originally decided, so there's no browser-support regression. The skip-list is scoped to directories that can structurally never contain an author-written skill (build output, dependency trees, VCS internals), matching how virtually every other dev tool (`.gitignore`-style conventions) already treats these paths.

**Alternatives considered**: making the OS picker show/jump to hidden dotfolders directly was considered — there is no browser API to do this (`showDirectoryPicker()`'s `startIn` option only accepts well-known folders or a previously-granted handle, not an arbitrary path, and there's no way to toggle "show hidden files" from JS). Addressed instead with inline UI copy pointing at the OS-level workaround (Cmd+Shift+. on macOS) plus the skip-list making "just select the parent folder" fast enough not to matter.

## Decision: where detection/parsing logic lives, and the client/server boundary

**Decision**: a new pure domain function, `scanLocalSkillFolders()` in a new `src/bcs/prompt-registry/domain/local-skill-source.ts`, reusing `parseSkillFrontmatter()` (from the sibling `domain/external-skill-source.ts`) and `MAX_FILE_SIZE_BYTES`/`MAX_SUPPORTING_FILES` (from `domain/prompt.ts`). It takes the already-read `{ relativePath, content }[]` entries and returns detected candidates, per-candidate validity (malformed/oversized → excluded, per FR-010), and intra-batch duplicate names (per FR-013) — no I/O, so no application-layer wrapper is needed (mirrors `determinePromptVersionKind`, an existing domain function barrel-exported with no application-layer wrapper). A new Server Action in `src/app/(app)/prompts/actions.ts`, `scanLocalSkillFoldersAction()`, wraps it with the same `requireActingUser()` auth check every other action in that file already uses (FR-009), and a second new action, `importLocalSkillsAction()`, registers the selected candidates via `createPrompt`/`publishVersion` exactly like `importExternalSkillsAction` (one independent transaction per skill) but never sets `sourceUrl` — this feature has no provenance-tracking requirement (unlike `001`), matching the spec's own scope.

**Rationale**: Next.js Server Actions are the safe, already-established boundary for a Client Component to reach real backend code — the framework replaces a `"use server"`-exported function with an RPC stub at build time, so its implementation and transitive dependencies (including `@/bcs/prompt-registry`'s Postgres/audit/etc. deps) never enter the client bundle. This is the exact mechanism `001`'s `fetchExternalSkillSourceAction` already relies on. It is *not* the same as a Client Component importing a plain (non-`"use server"`) BC export directly, which is the documented gotcha that broke a build previously (a real function's implementation and full transitive graph get bundled for real in that case) — that gotcha does not apply here because detection also goes through a Server Action, not a direct client-side BC import.

**Alternatives considered**: doing candidate detection/parsing entirely client-side (duplicating a small local copy of frontmatter-parsing logic in the client component, per the documented mitigation for the *other* class of gotcha) was considered and rejected here — it would duplicate `parseSkillFrontmatter`'s regex logic for no reason, since the safe Server Action boundary already avoids the bundling problem that mitigation exists for. Reuse is strictly better once a Server Action is in play.

## Decision: intra-batch duplicate name handling (FR-013)

**Decision**: `scanLocalSkillFolders()` groups all successfully-parsed candidates by name (post-frontmatter-resolution, matching whatever name each candidate would actually register under) and returns the set of names appearing more than once. The drawer's preview UI flags every candidate sharing a name in that set (visually, matching the existing red-bordered "collides with existing org skill" treatment `001`'s preview already uses for the *cross-batch* collision case) and disables selecting more than one candidate per conflicting name at a time.

**Rationale**: matches the already-answered clarification exactly, and reuses the existing preview UI's established visual language for "this candidate can't be registered as-is" rather than inventing a second distinct warning style.

## Decision: UI integration point

**Decision**: a third mode is added to `new-prompt-drawer.tsx`'s existing `NewSkillMode` union (`"blank" | "import"` → `"blank" | "import" | "upload"`), with its own mode-tab button and its own body panel, following the same structural pattern (state hooks, preview list, confirm button) as the existing `"import"` mode.

**Alternatives considered**: a wholly separate drawer/page for this feature was considered and rejected — the existing three-mode tab pattern in one drawer is a smaller diff, keeps "how do I get a new skill into the registry" as one discoverable entry point (the drawer's own header stays "New skill"), and Constitution Principle VIII ("a new drawer... MUST be built — or extended — as a shared primitive... rather than hand-rolled per feature") favors extending the existing drawer over introducing a second one.

## Testing approach

- `domain/local-skill-source.test.ts` — pure Vitest unit tests for `scanLocalSkillFolders()` (candidate detection at varying nesting depths, malformed/oversized exclusion, intra-batch duplicate detection, and a large-synthetic-batch case proving no artificial cap exists per FR-014) — no DOM/Testcontainers needed, mirrors `domain/external-skill-source.test.ts`.
- `local-folder-reader.test.ts` (NEW) — pure Vitest unit tests for the candidate-directory path-filtering half of `local-folder-reader.ts` only (given a flat list of relative paths, which ones fall under a matched `SKILL.md` directory) — no DOM needed, since this half never touches `File`/`FileList`. This closes a gap found during `/speckit-analyze`: FR-012/SC-005's "never transmits unrelated content" guarantee had an implementing task but no verifying one.
- `new-prompt-drawer.test.tsx` — extended with `renderToStaticMarkup`-based structural assertions for the new mode tab and its preview list, matching the file's existing style for the `"import"` mode, **plus** a new `axe-core` assertion (`expectNoCriticalOrSeriousAxeViolations`, already used by `shared/ui/drawer.test.tsx`) covering the drawer's actual rendered content across all three modes. `/speckit-analyze` found this was genuinely missing — `drawer.test.tsx` only axe-tests the generic `Drawer` shell with dummy children, never `NewPromptDrawer`'s real content, so neither the already-shipped `"import"` mode nor this feature's new mode had ever been checked against Constitution Principle VIII until now.
- `actions.local-import.test.ts` (NEW) — a Testcontainers-backed test for `runLocalSkillImportBatch`, a function extracted out of `importLocalSkillsAction` specifically to make this feature's per-skill create/publish/error-isolation loop (the entire mechanism behind User Story 3) independently testable. `importExternalSkillsAction`'s equivalent loop has no test today; `/speckit-analyze` concluded this is very likely because `requireActingUser()` calls `next/headers()`, which throws outside a real Next.js request — not because the loop itself doesn't need one. `runLocalSkillImportBatch(actingUser, skills)` takes an already-resolved actor object as a plain parameter instead, so a test can call it directly against a real Testcontainers Postgres with no `headers()`/cookie mocking required. `importLocalSkillsAction` itself stays a thin wrapper: resolve `actingUser` via `requireActingUser()`, then delegate.
- The thin browser-only glue that remains (`webkitdirectory` input handling, drag-and-drop `webkitGetAsEntry()` traversal, `File.text()` reads — as opposed to the pure path-filtering logic now covered by `local-folder-reader.test.ts`) is still not unit-testable under this repo's jsdom-less Vitest setup and is verified via live manual browser testing instead, matching this repo's established convention for browser-API-only wrappers.
